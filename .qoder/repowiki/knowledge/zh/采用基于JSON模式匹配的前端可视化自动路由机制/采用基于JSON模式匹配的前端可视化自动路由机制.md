# 采用基于JSON模式匹配的前端可视化自动路由机制

_来源：7877e84 → 7e09e16 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
前端聊天界面（ChatView）虽然实现了6个学术可视化组件，但缺乏从后端MCP工具获取数据并触发渲染的机制，导致组件完全不可用。同时，后端返回的结构化数据（如引用网络、质量雷达）需要一种统一的方式被前端识别并路由到对应的React组件，而非硬编码每个工具的调用逻辑。

## 决策驱动
- 解耦前后端交互逻辑
- 支持多种可视化类型的自动检测
- 提升用户交互体验（一键可视化）

## 备选方案
- **为每个可视化工具硬编码前端调用逻辑** _（已否决）_ — 优点：实现简单直观；缺点：每新增一个可视化工具都需要修改前端路由代码，维护成本高，耦合度高
- **基于JSON结构模式匹配的自动路由** — 优点：通用性强，只需在后端返回特定结构的JSON（如nodes/edges, dimensions），前端即可自动识别并渲染；支持在聊天消息中通过按钮动态触发；缺点：需要定义和维护JSON模式与组件的映射关系

## 决策
在 `desktop/src/components/ChatView.tsx` 中实现 `tryDetectJsonInResponse` 和 `routeToComponent` 函数，通过正则提取后端返回的JSON代码块，并根据字段特征（如 `nodes/edges` 对应 `CitationGraph`，`dimensions` 对应 `QualityRadar`）自动路由到相应组件。同时在 `MessageBubble` 中增加论文ID检测和可视化操作按钮，允许用户手动触发 `call_scholar_mcp` 并复用同一套路由逻辑。

## 影响
前端能够自动展示后端返回的结构化学术数据，无需为每个工具编写独立的渲染逻辑。新增可视化工具时，只需确保后端返回符合既定模式的JSON即可。增加了前端对JSON解析错误处理的复杂性。
