# 采用基于内存文件扫描的 Hybrid ID 解析机制

_来源：bc51cd3 → 35a8f17 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
系统需要支持通过 ULID、arXiv ID、DOI 或 Slug 等多种格式查询论文，但底层存储仍以 ULID 为主键。需要在不改变数据库主键结构的前提下，实现多格式 ID 到 ULID 的高效映射。

## 决策驱动
- 实现简单性（避免引入新的数据库索引或复杂查询逻辑）
- 数据规模可控（当前仅 440 篇论文，内存索引性能足够）
- 向后兼容性（保留 ULID 作为内部唯一标识）

## 备选方案
- **基于数据库查询的 ID 解析** _（已否决）_ — 优点：数据一致性由数据库保证，适合大规模数据；缺点：需要为 arxiv_id/doi/slug 建立额外索引，增加数据库查询复杂度
- **完全替换 ULID 为 arXiv ID** _（已否决）_ — 优点：简化 ID 体系，符合学术习惯；缺点：非 arXiv 论文无法覆盖，且修改主键导致巨大的向后兼容成本和代码重构
- **基于内存文件扫描的 Hybrid ID 解析（选中）** — 优点：无需修改数据库 Schema，实现极简，启动时一次性加载索引，读取速度极快；缺点：依赖文件系统状态，需在知识库更新后刷新缓存

## 决策
新建 `scholar/id_resolver.py` 模块，在应用启动或首次查询时扫描 `output/parsed/*.json` 文件，构建内存中的多格式 ID 到 ULID 的映射缓存。CLI 命令统一通过 `resolve_id` 接口处理输入 ID。

## 影响
实现了用户友好的多格式 ID 查询体验，同时保持了内部数据模型（ULID）的稳定性。但引入了缓存一致性问题，需在 `kb-update` 等写操作后确保索引刷新。
