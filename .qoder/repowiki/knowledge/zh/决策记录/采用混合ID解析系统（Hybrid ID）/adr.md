# 采用混合ID解析系统（Hybrid ID）

_来源：3351308 → bc51cd3 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
原有系统仅支持26字符的ULID作为论文唯一标识，用户难以直接通过常见的arXiv ID、DOI或标题slug进行查询，导致交互体验割裂。需要一种机制能统一接受多种格式的ID输入并解析为内部ULID。

## 决策驱动
- 用户体验（支持自然常用的ID格式）
- 向后兼容（保留ULID作为内部主键）
- 实现复杂度（避免引入重型依赖）

## 备选方案
- **完全替换ULID为arXiv ID** _（已否决）_ — 优点：ID更具语义化，无需映射；缺点：非arXiv论文（如会议期刊）无arXiv ID，覆盖率不足；修改现有数据库和文件结构成本巨大
- **基于数据库查询的ID解析** _（已否决）_ — 优点：数据一致性高，支持复杂查询；缺点：每次解析需访问数据库，延迟较高；对于440篇小规模数据显得过重
- **基于内存缓存的文件索引解析（选中方案）** — 优点：启动时扫描JSON元数据构建内存字典，查询极速；实现简单，无额外依赖；缺点：需在kb-update后刷新缓存；内存占用随论文数量线性增长（当前规模可忽略）

## 决策
新建 `scholar/id_resolver.py` 模块，实现 `IDResolver` 类。在应用启动或首次调用时扫描 `output/parsed/*.json` 构建 `any_id -> ulid` 的内存索引。所有CLI命令（如 `info`, `parse` 等）入口统一调用 `resolve_id` 将用户输入的 arXiv ID/DOI/slug 转换为内部 ULID。

## 影响
用户可以使用任意已知ID格式操作论文，提升了CLI和MCP工具的易用性。内部逻辑仍基于ULID，保证了数据一致性。需确保在知识库更新（kb-update）后重新加载索引以包含新论文。
